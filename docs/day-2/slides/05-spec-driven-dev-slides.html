Spec-Driven Development

AI models are excellent at pattern completion and poor at mind reading. A spec closes that gap.

12:20 PM·40 MIN·Lecture
01

What a Spec Is

A spec, short for specification, is a written description of what something should do, worked out before anyone builds it. Product and design teams have used them for decades.

An engineer writes what a feature needs to accomplish. A designer writes what a screen needs to show. An editor writes what a story needs to cover before a reporter starts. Same habit everywhere. Agree what "done" looks like before you start.

A useful spec has three parts. The requirements, what has to be true when it's finished. The constraints, what can't be true. The acceptance criteria, how you'll know it's actually done.

02

The Core Idea

Spec-driven development applies that same habit to working with an AI coding assistant. It inverts the usual workflow. The spec becomes the source of truth, code becomes something generated and checked against it.

AI models are excellent at pattern completion, matching what you ask against patterns they've seen, and poor at mind reading. A vague prompt leaves Claude guessing. A spec gives it enough to match your intent instead of inventing one. Works best on new, well-scoped work, less so on a large existing project's code.

03

The Checklist

  1. 1

    Specify

    What should it do, not how? What does "finished" look like? Only one reasonable reading, or several?

  2. 2

    Plan

    What's the approach? Whose judgment does this need, not just the model's?

  3. 3

    Implement

    Small, checkable pieces, not one giant leap. Does each one do what it said?

  4. 4

    Validate

    Does it match the spec? If not, was the spec wrong, or the build? Either way, the spec stays the authority.

spec-driven-starter-prompt.md

I want to build [describe the project].
Here's what I worked out:
Specify: [what it should do, what "finished" means]
Plan: [approach + what it has to work with]
Implement: [pieces you'll build and check one at a time]
Validate: [how you'll know it's done]

Turn this into requirements.md, architecture.md, and tasks.md.
Update CLAUDE.md to point to them, then treat them as the
source of truth.

Files that aren't updated when the project changes don't just go unused, they actively mislead.
